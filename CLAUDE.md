# CLAUDE.md

## What This Project Is
- Landing page + blog for TidyWL (the Chrome extension)
- Live at https://tidywl.com (custom domain on GitHub Pages)
- Repo: https://github.com/dominic-lam/tidywl-site
- Jekyll-based: GitHub Pages renders it server-side
- Deployed via GitHub Pages from main branch

## Tooling rule
Keep the site as simple as possible. No local build tools, no bundlers, no frameworks requiring `npm install`. Jekyll is the one exception — GitHub Pages runs it server-side, so authors only edit markdown and commit. Everything else (CSS, JS, landing page HTML) stays plain.

## File Structure
- `index.html` — production landing page. Uses Jekyll `{% include %}` tags for shared head/styles/theme-toggle/footer/scripts; all page-specific head content (title, meta, OG, JSON-LD) stays inline here.
- `_config.yml` — Jekyll config (permalinks, plugins, excludes). GitHub Pages reads this.
- `Gemfile` — pins `github-pages` gem for local preview (`bundle install && bundle exec jekyll serve`).
- `_includes/` — shared snippets: `fonts.html`, `theme-init.html`, `styles.html` (the big CSS block, shared with landing), `styles-blog.html` (blog-only typography), `theme-toggle.html`, `footer.html`, `scripts.html`, and `scripts-reviews.html` (landing only: two independent `<script>` elements, the featured carousel and the community marquee, so a throw in one cannot stop the other).
- `_layouts/` — `default.html` (blog pages) and `post.html` (extends default, adds post-specific markup + optional FAQ rendering).
- `_posts/` — blog posts in Markdown, filename `YYYY-MM-DD-slug.md`. Permalink pattern: `/blog/:slug/`.
- `_data/cws-rating.yml` — single source of truth for the Chrome Web Store aggregate rating **and user count**. Read via Liquid in `index.html` (the hero `.hero-stats` strip) and in `llms.txt`. The JSON-LD has not carried it since 2026-09-16 (see Key Constraints). Shape: `ratingValue`, `reviewCount`, `userCount`, `lastUpdated`. `userCount` keeps its comma for display and is a **floor** — the store rounds to a bucket, which is why the page renders it with a trailing `+`. Auto-updated weekly by `.github/workflows/update-cws-rating.yml`; do not hand-edit unless the workflow is broken.
- `_data/usage.yml` — the site's three first-party numbers: `deletedTotal` (videos **cleaned up**: deletions, plus likes removed before 1.6.0, which the extension counted together — never label it "deleted" in copy), `unlikedTotal` (likes removed), `movedTotal` (videos moved between playlists). Written **daily** by `.github/workflows/update-usage-total.yml` from `https://tidywl.com/api/stats`; do not hand-edit. Each `*Total` is a **floor**, rounded down to the nearest 1,000, because every place that renders one says *"over"* or carries a `+` — rounding up would make the copy false between runs. Each `*Raw` is the unrounded value that counter's **monotonic guard** compares against on the next run: the counters keep MAX-ever-reported and retired rows roll into `retired_total`, so they cannot legitimately fall, and a drop means a bad response rather than a real decline. **The run is all-or-nothing**: any counter that fails to parse, validate or clear its guard fails the whole run and leaves all three at the last good snapshot, because the file carries one `lastUpdated` and the copy dates all three figures to it — a stale number stays true, a misdated one does not. Rendered in four surfaces — the hero stat (deletions), the *"How many videos have TidyWL users actually cleaned up?"* FAQ answer (all three), that question's `FAQPage` JSON-LD, and `llms.txt` (which carries front matter solely so Liquid renders there). The quiet sentence under the hero stats that carried the other two left with the 2026-09-16 hero. `scripts.html` hydrates whichever of `#videos-cleaned` / `#likes-removed` / `#videos-moved` are on the page (today only the first), leaving any figure alone on failure rather than blanking it. **The markup figures are what non-JS crawlers index, which is most AI crawlers, so they must never be left hand-maintained** — the deletions floor went 39% stale in the 24 hours it was.
- `_data/cws-reviews.json` — **every written Chrome Web Store review**, newest first: `id`, `author`, `stars`, `text`, `date`, `version`, `lang`. Rewritten weekly by the `reviews` job below; **never hand-edit**, the next run overwrites it. Feeds two places, both filtered by the same config: the landing page's *More from the community* marquee (minus the featured ones), and the *What users say* section of `llms.txt`, which says how it is filtered. **`_data/reviews.yml` now drives only the featured carousel and the YouTube cards.**
- `_data/cws-reviews-config.yml` — what the marquee shows, applied at **build** time so an edit takes effect on the next push rather than the next Sunday: `min_stars` (4), `min_length` (25 characters, so one-word reviews stay out), `max_shown` (60, newest first), `hide` (review ids never to show — the kill switch for anything offensive or naming a private person), `lang` (fixes where Google guessed a language wrong) and `labels` (the language pill's text). A review featured in `_data/reviews.yml` is skipped automatically, so nothing appears twice.
- `scripts/templates.test.mjs` — reads the real templates and fails if any review field is printed without its escaping, if the two review outputs stop applying the same filters, if a store rating or review comes back into the JSON-LD, if any page an assistant reads brings back a retired claim ("Runs locally", "no data leaving", "no server backend", "sends anything off", "Two things do leave", the total called "deleted", Pro "ships with" 2.0), or if a marker digit is written as text. Run it after any edit to `index.html`, `llms.txt`, `/pricing/`, `/tutorials/` or the three privacy-sensitive posts.
- `scripts/fetch-cws-reviews.mjs` (+ `.test.mjs`) — the weekly review fetcher. Node 18+, **no dependencies**, excluded from the built site. Run it by hand with `node scripts/fetch-cws-reviews.mjs`; test with `node --test scripts/fetch-cws-reviews.test.mjs` (naming the file — Node 24 fails on the bare directory). It calls the store's own public reviews RPC, and two things about that RPC are not obvious: **`hl` filters reviews by language** (English alone returned 30 of 42 on 2026-09-16, with a total and no continuation token that made 30 look complete), so it sweeps ~50 languages and unions by id; and the RPC id and session values are **read from the page each run**, since they rotate with store deploys. It refuses to write an empty list or one under half the committed count, exiting non-zero and leaving the file alone.
- `.github/workflows/update-cws-rating.yml` — scheduled (Sun 06:00 UTC) + `workflow_dispatch`, two jobs. **`update`** scrapes the CWS listing HTML, validates the parsed rating/count (range, positive int, >=50% of previous), writes `_data/cws-rating.yml`, and commits as `github-actions[bot]`; on parse failure it uploads the fetched HTML + headers as a 30-day artifact. CWS does not expose JSON-LD or microdata, so parsing anchors on `"X out of 5"` and `"N ratings"` text — if Google ever redesigns the markup, expect a Sunday failure email and the artifact will show the new shape. **`reviews`** runs after it whatever its result, tests and runs the fetcher, and commits `_data/cws-reviews.json` only when a review was added or changed; a failure is its own red job and uploads the fetch log. Its fetch step sets `pipefail` on purpose: the default run shell does not, and without it `node … | tee` reports tee's success, turning a refused write into a silent green "no new reviews".
- `help/index.html` — the support page (common fixes, email). It was the landing page's *Need help?* section until 2026-09-16; the header drawer and the footer link to it.
- `assets/chrome-logo.svg`, `assets/firefox-logo.svg` — the browsers' own logos, unmodified (sources in each file's first line), on the landing page's two install buttons.
- `blog/index.html` — blog post listing page.
- `DESIGN.md` — notes from the UI rebuild (some `../../` path refs are stale from the original design kit)
- `sitemap.xml`, `robots.txt`, `llms.txt` — SEO/GEO files at root
- `CNAME` — GitHub Pages custom domain config (`tidywl.com`)
- `config/api-config.json` — YouTube response path config consumed by the extension
- `config/announcements.json` — in-product "What's new" banners consumed by the extension
  - Fetched from `https://tidywl.com/config/announcements.json` by
    `src/content-scripts/content.js` (`fetchAnnouncements`) in the extension repo
  - Rendered as dismissible cards in the TidyWL dashboard (see
    `src/dashboard/dashboard-data.js::checkAnnouncements` and
    `src/dashboard/dashboard-ui.js::renderAnnouncements`)
  - Expected shape: `{ "announcements": [ { id, title, bullets[], type, expires_at }, ... ] }`
    — **plural array**, not a singular `announcement` object
  - `id` is used for dismissal tracking (stored in `chrome.storage.local`
    under `wl_announcement_dismissed_ids`); `expires_at` auto-hides the entry;
    `type` maps to a banner variant (e.g. `info`)
- `assets/` — static images (icon128.png, small_promo_tile.png, og-image.png)
- `.gitignore` — standard ignores

## Key Constraints
- CNAME file is managed by GitHub Pages — do NOT modify or delete it
- No local build tooling beyond Jekyll (see Tooling rule above)
- Custom domain is tidywl.com (apex), www.tidywl.com redirects to apex
- Canonical URL is https://tidywl.com/ — any new meta tags or
  internal links should use this, not the github.io URL
- Landing page `<head>` keeps its SoftwareApplication + FAQPage JSON-LD blocks inline. Do not move them into Jekyll layouts/includes — they're tied to the landing page content and the GEO work treats them as sacred.
- **`cws-rating.yml`'s `reviewCount` key holds the store's RATING count** ("67 ratings"), not the number of written reviews. `llms.txt` says "N ratings, M of which include a written review". The hero labels it "ratings" too, visibly and in its `aria-label` (since 2026-09-16). Never call ratings reviews in copy an assistant will quote.
- **No store rating and no store review in the JSON-LD (removed 2026-09-16).** Google's review-snippet guidelines: "Don't aggregate reviews or ratings from other websites." Every rating and review on this site comes from the Chrome Web Store, so the markup risked a manual action for no gain. The price: `SoftwareApplication` needs `aggregateRating` or `review` for Google's software-app rich result, so the page has none, which it was not entitled to anyway. The rating and reviews stay visible on the page and in `llms.txt`, which is what AI assistants read. **If a review string ever goes back into JSON-LD**, it needs `| jsonify` and then `<`, `>` and `&` rewritten as their backslash-u escapes, because `jsonify` lets `</script>` close the block. On 2026-09-16 the agent tooling converted typed backslash-u sequences into the literal characters (`replace: "<", "<"`, a silent no-op): build the backslash from `chr(92)` / `String.fromCharCode(92)` and verify by counting bytes.
- **Anything from `_data/cws-reviews.json` is printed through `| escape`.** It is strangers' text, published every week without anyone reading it first; printed raw, a review containing markup becomes script on tidywl.com. Checked 2026-09-16 by building a copy of the site with a hostile review in it. The same goes for any future auto-fetched source.
- **The community marquee only moves when it can be stopped.** Without JS, or under `prefers-reduced-motion`, it is a plain sideways scroller a keyboard can scroll. `scripts-reviews.html` adds the motion, a pause button outside the row (inside it, focusing the button would pause the row and pressing Start would seem to do nothing), and a second copy of every card for a seamless loop, marked `aria-hidden` and `inert`. Hover and keyboard focus pause it, and a focused card is brought into view by moving the animation — while it moves, the row's own scroll is held at zero, because focusing a link still scrolls an `overflow:hidden` box and the two together pushed the card out of view.
- **The landing page, since 2026-09-16:** header and hero on one "stage" (`.stage-top` + `.hg`), YouTube's Watch Later page against the dashboard with four numbered pain → fix rows, then the annotated dashboard tour with *Getting started*, reviews, *Why I built this* with the install buttons, six features plus *All features*, FAQ, privacy. Phones get the demo video in the hero and a *Send the link to my computer* hand-off instead of install buttons (`scripts.html`). The desktop demo section sits in a Liquid comment in `index.html` until the new recording exists. Its spacing is cut to fit a 900px-tall screen; on screens 1040px tall and more it opens up, and on large screens the hero and the tour scale together in `zoom` steps (1.12, 1.25, 1.4), each gated on a height at which the scaled hero still ends on the first screen. Re-measure those gates if the hero's content changes. Built from a review by two designers and two users; the reasoning is in that commit.
- **Red has three tokens.** `--accent` is the brand red for large type and marks only. White text on red fills with `--accent-fill` (white on `--accent` is 4.20:1, under the 4.5 minimum), and small red text uses `--accent-text`. All three, and the landing stage's `--stage-*` / `--tour-bg` tokens, are defined in the base `:root` and in both dark blocks of `styles.html`.
- Reviews carry no structured data at all: not in JSON-LD (above), and not as Schema.org microdata on the visible cards (`itemscope`/`itemtype`/`itemprop`), which once triggered "Missing field itemReviewed" and duplicate-entry warnings in GSC. Keep the visible cards as plain HTML.
- **Copy an AI assistant will quote must match what the extension sends (2026-09-16).** Since 1.6.0 it sends usage counts, and since 2.0 a Pro subscriber's licence check; Send to Gemini Notebook is the one feature that sends the user's *YouTube data*. So scope any privacy line to "your YouTube data" or "your playlist", never to "anything" or "data", and count what leaves as three things. Perplexity repeated the old "no telemetry" line in September 2026. `scripts/templates.test.mjs` bans the retired phrasings.
- **Text is what crawlers get, so nothing is glued together.** Decorative digits on markers (`.pin`, `.n`, `.num`, `.step`) come from `data-n` through `[data-n]::before` in `styles.html`, not from text. Where CSS shows one of two variants, or puts a label and its line in separate boxes, an `.sr-only` separator (". ", " — ", ": ") sits between them so a text extractor reads two phrases, not one fused word. `.sr-only` is absolutely positioned, so it never takes a grid or flex slot.
- **`robots:` in a page's front matter** (default layout) emits a robots meta tag; `/checkout/success/` uses `noindex`. `sitemap: false` alone only keeps a page out of the sitemap.

## Common Tasks
- Updating landing page copy → edit `index.html` directly, commit, push, GitHub Pages auto-deploys
- Adding a blog post → create `_posts/YYYY-MM-DD-slug.md` with frontmatter (`title`, `description`, `date`, optional `og_image`, optional `last_modified_at`, optional `faq:` list of `{q, a}` items). Write body in Markdown. Commit and push; GitHub Pages renders the post at `/blog/slug/`.
- `last_modified_at` (optional, `YYYY-MM-DD`) — set it when you **substantively revise** a post or a page. On any page, `jekyll-sitemap` turns it into the sitemap's `<lastmod>`; `index.html`, `/pricing/` and `/tutorials/` carry one since 2026-09-16, so bump it when their content really changes. It drives `dateModified` in the post's `BlogPosting` JSON-LD and renders an "Updated" line next to the publish date, but only when it differs from `date`. Do not bump it for a typo: a freshness signal that does not correspond to changed content is worse than no signal. When absent, `dateModified` falls back to `date`, because schema.org reads a missing `dateModified` as unknown rather than "never revised".
- Schema.org entities are linked by `@id`, not restated. `_includes/schema-organization.html` defines `Organization` once at `{{ site.url }}/#organization`, and the landing page's `SoftwareApplication`, `Blog`, and every `BlogPosting` reference it via `"publisher": { "@id": ... }`. It is an include because the landing page and `_layouts/default.html` have separate `<head>` blocks; duplicating the literal would let three slightly different Organizations drift apart. This does **not** contradict the rule below about keeping the landing page's `SoftwareApplication` + `FAQPage` inline — those two stay where they are.
- Adding screenshots → drop in `assets/` folder, reference with absolute path (`/assets/...`) from blog pages, relative path from `index.html`
- SEO changes → `og:` tags and canonical link are in `<head>` of `index.html` (landing) and `_layouts/default.html` (all blog pages)
- Local preview → `bundle install` once, then `bundle exec jekyll serve` (preview at http://127.0.0.1:4000)
